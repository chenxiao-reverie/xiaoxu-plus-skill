## 一、三档判定

| 档 | 判定条件 | 成本 | 产出形态 |
|----|---------|------|---------|
| `L0` 直问 | 上下文已足够；或纯偏好/意愿类问题 | 0 | 直接出题 |
| `L1` 快查 | **默认档**。不知道答案就写不出靠谱选项 | 1–3 次检索（双语各一组） | 提问弹药 1–3 枚 |
| `L2` 深调研 | 答案决定「该不该做」 | 四阶段全跑 | 可据以决断的结论 |

**判定口诀**：
> 不知道答案能不能写出 2–4 个互斥选项？能 → L0；不能 → L1；连「该不该做」都定不了 → L2。

## 二、L1 五种快查模式

L1 只服务一个目的：**把填空题升级成选择题**。

### 模式 1：术语校准

同一个词在不同行业指完全不同的东西，问错方向整条线都废。

| 用户说 | 可能是 | 查询 |
|--------|--------|------|
| 「看板」 | BI dashboard / kanban board / 大屏 | `"dashboard vs kanban board difference"` + 「数据看板 任务看板 区别」 |
| 「小程序」 | 微信小程序 / 支付宝小程序 / H5 套壳 | `"wechat mini program vs h5"` + 「小程序 H5 区别 选型」 |
| 「自动化」 | 定时任务 / RPA / 工作流引擎 / AI Agent | `"rpa vs workflow automation vs ai agent"` |
| 「报表」 | 固定报表 / 自助 BI / 明细导出 | `"operational report vs analytical report"` |

**产出**：把用户的口语词替换成行业标准词，并用标准词出题。

### 模式 2：行业惯例

这个场景的成熟做法是什么？直接作为选项来源。

```
"[domain] best practices 2026"
"[domain] standard workflow"
「[行业] 标准流程」「[业务] 常规做法」
```

### 模式 3：量级锚定

用户说「便宜点」时，直接给数量级选项，比追问有效十倍。

```
"[thing] development cost estimate"
"[thing] build time months"
「[东西] 开发成本 大概」「[东西] 工期」
```

### 模式 4：可行性红线

有些方向不用问用户，查一下就知道走不通（资质、平台政策、合规、技术限制）。

```
"[thing] regulatory requirements China"
"[platform] api policy limits"
「[业务] 资质要求」「[平台] 接口限制 政策」
```

> 红线类结论必须给出处，否则不要用它否决用户的想法。

### 模式 5：竞品参照

让用户「指认」比让用户「描述」容易得多。

```
"[category] product comparison 2026"
"[category] alternatives review"
「[品类] 产品 对比」「[品类] 有哪些」
```

**用法**：列出 2–3 个真实产品作为选项 —— 「你想要的更像 A 还是 B？」

## 三、提问弹药卡

调研完不要给用户念报告，只交弹药。每枚弹药必须写清「它改变了什么」：

```
弹药：<一句话结论，带数字>
来源：<机构/站点> · <链接> · <检索语言> · <日期>
改变了什么：<原计划选项 → 现在应新增/删除/修改哪个选项>
```

**「改变了什么」为空 = 这枚弹药无效**，直接丢掉，不要写进对话。

> 这是防止信息囤积的唯一闸门。调研不是为了让 AI 显得博学，是为了让选项更准。

## 四、L2 深调研

### 5 个触发条件（命中任一即可）

1. 该答案决定**「该不该做」**，而不是「怎么做」
2. 关键假设是 **P0**（错了整个需求作废）
3. 用户明确说**「我不知道，你帮我查」**
4. 涉及**合规 / 资质 / 成本的硬门槛**
5. 决策核心是**中外 / 跨市场对比**，单边信息不足

### 四阶段

**① 广泛探索**：宽泛查询摸格局，识别 3–5 个关键维度与不同立场。

**② 深入挖掘**：逐维度定向检索，**抓取全文**而非只看摘要，顺藤摸瓜追溯一手来源。

**③ 多样性与交叉验证**：六类信息全覆盖 —— 事实数据 / 实例案例 / 专家观点 / 趋势预测 / 横向对比 / 挑战批评。

**④ 综合自检**：6 项全过才算完成，任一项为「否」就继续检索：

- [ ] 至少从 3–5 个不同角度检索过
- [ ] 已抓取并通读最重要来源的全文
- [ ] 掌握了具体数据、实例与专家观点
- [ ] 既了解积极面，也了解挑战与局限
- [ ] 信息是最新的，且来自权威来源
- [ ] 同时覆盖英文与中文来源

### 六类信息查询模板（查询串用英文）

| 类型 | 查询串 | 目的 |
|------|--------|------|
| 事实与数据 | `"[topic] statistics"` / `"[topic] market size"` | 硬证据 |
| 实例与案例 | `"[topic] case study"` | 真实落地 |
| 专家观点 | `"[topic] expert analysis"` | 权威视角 |
| 趋势预测 | `"[topic] trends 2026"` | 未来走向 |
| 横向对比 | `"[topic A] vs [topic B]"` | 替代方案 |
| 挑战批评 | `"[topic] limitations"` | 保持平衡 |

## 五、双语检索

**查询串用英文，结论用中文。** 两者覆盖不同信息生态，应当并行。

| 议题特征 | 配比 |
|---------|------|
| 技术、学术、前沿研究 | 英文为主（70–80%） |
| 全球市场、跨国企业、宏观趋势 | 英文为主 |
| 中国政策、A 股、国内数据 | 中文为主（60–70%） |
| 国内产品、本地落地、区域案例 | 中文为主 |
| 中外对比 | 双语均衡，两侧各跑完整一组 |

不确定时默认**双语各跑一组**，成本远低于漏掉关键信息。

**术语转换三步**（避免硬译导致整条检索线失效）：
1. 先用中文搜一次，从权威源提取**官方英文术语**
2. 用该术语展开英文检索
3. 外来概念（RAG / agentic workflow / OKR）**直接用原词**，不要回译

## 六、时间意识

构造查询前先看当前日期，按用户意图选精度：

| 用户意图 | 精度 | 示例 |
|---------|------|------|
| 「今天」「刚发布」 | 月 + 日 + 年 | `"tech news February 28 2026"` |
| 「本周」 | 周区间 | `"releases week of Feb 24 2026"` |
| 「最近」「最新」 | 月 + 年 | `"breakthroughs February 2026"` |
| 「今年」「趋势」 | 年 | `"industry trends 2026"` |

> 需要精确到日时，绝不能退化成只写年份。

## 七、停止条件

| 档 | 何时停 |
|----|--------|
| L1 | 能写出 2–4 个互斥选项 + 一个有证据的推荐 → **立即停** |
| L2 | 四阶段自检 6 项全过 → 停 |

**L1 的过度调研是 Plus 最常见的浪费**：用户可能一句话就回答了，你查二十分钟等于白干。

## 八、查不到怎么办

**绝不编造。** 三种处理：

1. **明说缺口**：「这个数据我没查到可靠来源」+ 说明查了哪些方向
2. **转成提问**：「这个数你手上有吗？没有的话我们先按 X 假设推进，后面再校准」（假设入台账，标 P0）
3. **降级结论**：「目前只能确认量级在万元级，具体要看供应商」

> 一条诚实的「不知道」，比三条编造的「研究表明」更有价值。
