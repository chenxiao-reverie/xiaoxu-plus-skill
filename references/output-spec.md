## 二、假设台账

| ID | 假设 | 类型 | 证据 | 状态 | 若错会怎样 |
|----|------|------|------|------|-----------|
| H1 | 现有系统有可用 API | P0 | 用户口述「应该能拉」 | ⚠️ 待验证 | 整个自动化方案不成立，退回人工 |
| H2 | 老板接受看板替代周报邮件 | P1 | 无 | ❓ 未知 | 做出来没人看 |

**字段规则**：
- `类型`：`P0`（错了需求作废）/ `P1`（影响方案优劣）/ `P2`（无关紧要）
- `状态`：`✅ 已证实` / `⚠️ 待验证` / `❌ 已证伪` / `🤝 用户承接风险`
- `若错会怎样`：必须写具体后果，不能写「有影响」

**什么时候写**：用户说出「应该」「大概」「一般来说」时，立刻记一条。**这些词是假设的信号灯。**

## 三、决议日志

| # | 分叉点 | 选项 | 结论 | 理由 | 否决项 |

## 五、填写硬规则

1. **§0 必须由用户确认**，且要能独立读懂——不能出现「上述」「该系统」这类需要上下文才能理解的指代
2. **§2 / §5 禁止模糊词**：尽快、尽量、适当、差不多、合理、较高、若干 → 出现即视为该项未通过
3. **§4「不做」不得少于 2 项**
4. **§7 所有 P0 假设状态不得为 ❓ 或 ⚠️**
5. **§8 每条决策必须有否决项**
6. **§9 每条证据必须带来源与日期**，无来源的结论移入 §10 开放问题
7. **§11 逐项打勾**，不允许「综合判断通过」
8. **6–7 分收敛**必须在开头加未确证项声明

## 六、交付格式

首轮已确认格式（Markdown / HTML / 两者）。**确认过的不再问第二次。**

### Markdown（默认）

- 单文件，命名 `<项目名>-需求确凿书.md`
- 沿用第四节模板，12 节齐全
- 可直接贴进文档、PR、知识库继续编辑

### HTML

- **单文件**：`<style>` 内嵌，无 CDN、无外部字体、无 JS 依赖——双击就能打开，断网也正常
- 命名 `<项目名>-需求确凿书.html`
- 结构：`<header>`（标题 + 确凿度 + 轮次 + 模式 + 日期）→ 12 个 `<section>`，每节带 `id` 供锚点跳转
- 样式要求：
  - 一个主色 + 中性灰，不超过两套色
  - 表格边框浅、行高充足、数字列右对齐
  - 正文 14–15px、行高 1.7，字体栈优先系统字体（`-apple-system, "PingFang SC", "Microsoft YaHei", sans-serif`）
  - `@media print` 下隐藏锚点导航、避免表格被分页切断
- **禁止**：交互组件、图表库、动画。它是文档，不是网页应用

### 两者都要

1. 先出 Markdown（作为源）
2. 再按 Markdown **逐节**转 HTML，内容不得增删
3. 两份同名不同扩展，放同一目录

### 一致性校验（生成后逐项自查）

- [ ] HTML 与 Markdown 章节数一致（12 节）
- [ ] 数字、日期、验收标准、否决项与 Markdown 完全相同
- [ ] HTML 断网后仍能正常显示
- [ ] 未混入 Markdown 里没有的内容

1. 直接转开发任务清单（我按 §4 拆里程碑）
